# Domus Climate — CLM.2 HOUSE configuration

This phase turns Settings → Casa → Clima into a real setup editor backed by the Home Assistant integration store `domusos.climate.v1`. The document belongs to the house. The browser holds only an unsaved draft. The previous `ClimateSystem` and preview fixtures remain presentation concepts; the persisted `ClimateHouseConfig` is a separate, closed contract.

## Contract and lifecycle

The stored envelope is `{schema:"domusos-climate",version:1,revision,config}`. The required config fields are `version`, `zones`, `endpoints`, `circuits`, `generators`, `profiles`, `schedules`, and `strategy`. CLM.2A adds optional, strictly parsed `operatingMode`, `controlMode`, `auxiliaries`, and `equipmentGroups`. CLM.4A uses the previously reserved `profiles` and `schedules` for [user programs](domus-climate-profiles-schedules.md); `strategy` remains `null`. Operating mode is Domus intent, never inferred from a physical device state. The store contains no runtime readings, demand, override, sensor health, dew point, active generator, or device state.

Zones have a stable ID, display name, optional HA area ID, one primary temperature entity, ordered fallback entities, optional humidity reference with the same ordered fallback pattern, and reciprocal endpoint IDs. V1 allows one area or none; a later schema version can add multiple area references while keeping the zone ID. An optional zone mode is `follow_house` or `off`, preventing opposite zone heat/cool intent. Endpoints are logical terminals with a zone ID, optional hydronic circuit ID, explicit capabilities, one primary `climate.*`, `switch.*`, `valve.*` or `input_boolean.*` entity, and optional typed secondary controls. The semantic setpoint is `room_temperature` or `none`. Circuits have reciprocal zone/endpoint/generator links, explicit heat/cool capabilities, optional climate controller, supply setpoint and component bindings, cooling safety metadata and generator preferences. Generators distinguish boiler, thermostove, heat pump, and other, list separate `space_heating`, `space_cooling`, and `domestic_hot_water` services, and use either no setpoint or `generator_water_temperature`. A thermostove requires a climate entity with a supported water range and step. Room, circuit supply and generator setpoints are distinct.

Every write parses the full document with required and explicitly optional keys, size and collection bounds, stable IDs, unique bindings, and reciprocal links. It validates referenced HA areas and live entities. Temperature and humidity sources require their corresponding sensor type or a climate entity with a current reading. Climate terminal heat/cool roles require matching `hvac_modes`; switch and valve actuators have no room setpoint. Unknown or incompatible references are rejected. A temperature source chooser resolves primary first, then fallbacks in order, and returns no source if none has a finite reading; it does not command a device.

CLM.2A retains `domusos.climate.v1` and envelope version 1 because CLM.2 has not reached main or a release. The original CLM.2 radiator document remains valid and unchanged on parse/serialize. New fields are optional and closed: unknown fields still fail. No cosmetic migration or store rewrite occurs. A newly saved extended document uses the same revision and idempotence rules. Scenario A–F fixtures cover existing AC/TRV plus boiler/stove, heat-only radiant, reversible radiant with humidity and shared dehumidifier, fan coil, multisplit, and a mixed house. See [general climate architecture](domus-climate.md#general-climate-architecture-clm2a) for decisions C16–C27 and future constraints.

`domusos/climate/get_config` returns `{state,revision,config}`; `domusos/climate/save_config` accepts `{config,expected_revision}`. An absent store starts at revision 0. A successful write increments the revision; the same config with the current revision is idempotent. Stale revisions return `conflict`. Corrupt, unsupported, and migration-failed stores remain untouched and block writes. A failed storage write leaves the in-memory revision unchanged. Migration is version gated; no legacy format is silently assumed.

`climate.view` is granted to administrator, resident, member, and wall panel roles. `climate.manage` requires an active HA administrator and is never user grantable. Both WebSocket commands are registered in Access Control with backend enforcement and denial audit. The save handler also requires HA admin, and the manager checks again before writing. This is distinct from future daily climate control. Successful changes record principal and revision in the bounded Domus audit service.

The page loads the real store before showing setup. Absent configuration offers a real editor and a separate demo preview. A saved configuration shows real zone names and mapping counts, with editing only for administrators. Corrupt, unsupported, unavailable, and conflict states are explicit. The editor includes zone/area selection, primary and ordered fallback sensors, zone device roles and related controls, radiator valves and controller, generator services and water setpoint kind. Save and cancel act on one draft; unsaved changes warn before page unload. The preview never writes the store.

## Decisions

- **C9 — persistence:** A dedicated versioned HA Store owns climate HOUSE configuration; no profile, device, or local storage copy is authoritative.
- **C10 — zone/area cardinality:** A zone references zero or one existing HA area in V1. A later schema version may add multiple areas while preserving the zone ID.
- **C11 — temperature fallback:** The primary entity is tried first, then validated fallbacks in saved order. No finite reading means no selected source.
- **C12 — endpoint roles:** Explicit `room_heater`, `room_cooler`, and `radiator_trv` roles can coexist on one logical endpoint where compatible; the same AC entity is not duplicated to express heat and cool.
- **C13 — generator setpoint:** `generator_water_temperature` is separate from `room_temperature` and validated against the HA entity's range and step. Boiler control can remain only at the circuit controller.
- **C14 — backend capabilities:** `climate.view` and `climate.manage` are separate, backend enforced capabilities. Daily control is a future decision.
- **C15 — roles:** Administrator can view and manage; resident, member, and wall panel can view; restricted and locked cannot view; management requires HA admin and is never user grantable.

Linux backend CI is part of the existing Home Assistant matrix (2025.1 and 2026.2.3). The first leg explicitly includes the new config and manager tests; the current leg runs all `tests_python`. No release package is built in this phase.
